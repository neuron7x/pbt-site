# ПБТ: доказова візуальна верифікація

**PR-03, залежить від тем із PR-02 (issue #4).** Вихідна гілка: `main@7be8bba75ef612bfc424f31b894e354876d4525b`. Результат цього PR — не нова рекламна картинка, а інструмент, який дозволяє приймати або відхиляти конкретний дизайн за реальними браузерними знімками.

## Метод

- **Профілі:** Chromium, `prefers-reduced-motion: reduce`, локальний сервер, фіксовані CSS-пікселі й колірна схема, очікування локальних шрифтів.
- **Матриця:** кожна з тем `sky` та `precision` окремо: 1440×900 (герой/роботи/парк/калькулятор/доказ/заявка); 1366×650 (герой); 1024×768 (герой/парк); 820×1180 (герой); 390×844 (герой/роботи/парк/калькулятор/заявка); 320×568 (герой). Разом **2 теми × 6 екранів**.
- **Артефакт:** `artifacts/shots/manifest.json` + PNG із `sha256`, байтами, фактично перевіреними розмірами, ID теми та секції. Повна матриця обов’язкова, зразок: `precision--mobile-390--top.png`.
- **Сторож:** помилково відновлена тема, відсутній заголовок/CTA/розділи, горизонтальне переповнення, помилки JS, зламані видимі зображення, пошкоджений PNG, неправильний хеш або відсутній кадр → статус FAIL. Нічого не пропускаємо під виглядом «успішно».
- **Медіа:** `make media-audit` створює хеш-маніфест для локальних активів і застосовує `config/visual-budgets.json` (ліміти регресії). `make gate` тепер включає цей перевірювач.

## Запуск

```bash
python -m pip install --require-hashes -r requirements.txt
python -m playwright install --with-deps chromium webkit
make gate
make run
# інший термінал
make shots
# результат: artifacts/shots/*.png, artifacts/shots/manifest.json
make media-audit
# результат: artifacts/media-budget.json
```

### Порівняння двох перевірених версій

Зробіть `make shots` на базовій і кандидатній гілці однаковою версією Chromium і збережіть їх у двох окремих теках. Потім:

```bash
python tools/compare_shots.py artifacts/baseline artifacts/candidate artifacts/diff
```

Порівнювач спочатку перевіряє повну матрицю, CRC PNG, SHA-256, розміри й версію браузера. Якщо хоч один доказ невалідний — **FAIL**. Вихід: `comparison.json`, `README.md` із числовими відмінностями та контакт-листи «до / після / посилена різниця» для ключових кадрів. Ці цифри **не перетворюються на оцінку естетики**: зміна великої частки пікселів не означає покращення.

GitHub Actions `.github/workflows/visual-evidence.yml` запускає повний гейт уже на **складеній гілці PR #2 + PR #3** та повторює перевірки без доступу на запис у репозиторій, з SHA-pin для сторонніх Actions. Знімки зберігаються в GitHub artifacts 7 днів. Не публікувати серверні журнали чи дані заявок.

## Межі тверджень

| Дані | Що підтверджують | Чого НЕ підтверджують |
|---|---|---|
| SHA-256 скриншота, PNG dimensions | Збережено конкретний кадр саме цих пікселів | Дизайн естетичний або кращий за конкурентів |
| Відсутність overflow/JS-errors у 7 профілях | Технічні інваріанти конкретного запуску | Усі пристрої, браузери, способи взаємодії пройдені |
| `media-budget.json` | Розміри і хеші файлів у репозиторії | Обсяг завантаження сторінки або реально отримані байти мережі |
| `transfer_bytes_observed` | Діагностичні байти Resource Timing в одному лабораторному запуску | TTFB/LCP/INP/CLS користувачів у 75-му процентилі |
| `field_* = null` | Вимір не проводився | Нульова затримка, нульові зсуви або green Core Web Vitals |
| Статичний `reduced-motion` | Контент без руху відображається читабельно | Якість і контраст кожного кадру рухомого відео |

**Зафіксований інвентар `main`: 160 медіаактивів, 116 103 276 байтів (≈110,72 MiB).** Це повний розмір репозиторних активів, а не розмір однієї сторінки чи її першого рендера. Поточні ліміти — регресійні стелі, **не преміальна ціль продуктивності**. Окрема optimization-ітерація має зменшити їх і виміряти реальний трафік.

## Якість, яку ще слід довести

1. **WCAG 2.2 AA:** axe + ручні клавіатурні сценарії; окремо контраст тексту на реальних відеокадрах.
2. **Core Web Vitals:** польові дані (CrUX/RUM), 75-й процентиль окремо mobile/desktop; good LCP ≤2,5 s, INP ≤200 ms, CLS ≤0,1. Навіть успішний `make shots` не є PASS CWV.
3. **Lighthouse:** 3 cold-load виміри під однаковими умовами CPU/мережі, зафіксувати сирі звіти, не підміняти «бал» саморобною метрикою.
4. **Visual acceptance:** затвердження власником реальних desktop/mobile знімків PR #2 із цією ж матрицею; перевірка довіри до джерела відео і фотографій.
5. **CRM trust:** API webhook, HMAC, outbox і цифри каталогу не змінюються цим PR; ціни й ПДВ залишаються рішеннями власника.

Нормативні джерела: [NIST SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final), [WCAG 2.2](https://www.w3.org/TR/WCAG22/), [Google Web Vitals](https://web.dev/articles/vitals).

## Issue #4 — послідовність інтеграції

PR #2 додає один `site.css` із перемикачем тем та відновленням вибору до CSS. PR #3 містить єдиний інструмент скриншотів, який **fail-closed** вимагає обидві теми в усіх шести профілях. PR #3 спрямований на гілку PR #2, поки вона не злита в `main`: це **stacked PR**, а не незалежний зелений доказ для основної гілки. Після злиття PR #2 PR #3 можна перенаправити на `main` і перевірити повторно. Обидва PR залишаються Draft до доказів і схвалення власника.
